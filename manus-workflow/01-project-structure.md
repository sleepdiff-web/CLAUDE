# Phase 0 — Project boundary (get this right first)

Before you build anything, decide how many Manus projects you need. This is the decision
people botch, and it quietly ruins output quality.

## The rule: one project = one core buyer problem

A Manus project maps to **one buyer problem**, not one product and not one angle.

- **Too broad** — everything in one project. Manus pulls the wrong context, every script
  gets watered down because the brain is too scattered.
- **Too narrow** — a project per angle. You end up babysitting 20 half-empty projects that
  never accumulate enough context to learn anything.
- **Right** — one project per core buyer problem. Tight, condensed, and it keeps learning.

## Example (supplement brand)

Take a product with a big TAM and multiple buyer problems. Each buyer problem is its own
project; the angles live *inside* it.

```
PRODUCT: (e.g. a sleep / recovery supplement)

  Project A — "Can't fall asleep / racing mind at night"     ← one project
      angles: wired-but-tired, doomscrolling loop, cortisol-at-night,
              partner-keeps-me-up, Sunday-scaries, ...

  Project B — "Wake up groggy / poor sleep quality"          ← one project
      angles: 3am-wakeups, no-deep-sleep, snoring/partner, aging-sleep, ...

  Project C — "Daytime energy / focus crash"                 ← one project
      angles: 2pm-slump, brain-fog, caffeine-dependence, ...
```

If you only have **one** core buyer problem, that's easy — you have exactly one Manus project.

## Inside a project

The project **holds the buyer problem**. The **angles live within it** — you don't make a
project per angle. A single buyer problem like "racing mind at night" holds dozens of angles
(the guilt of lying awake, the partner it affects, the 3am spiral, the productivity cost the
next day…). All of those share the same brain, so they all belong in the same project.

## Product-selection side note (worth internalizing)

The reason "when do you kill a test?" rarely comes up in this system: pick a product whose
TAM can *support this structure* — multiple big, bleeding-neck buyer problems. If joint-pain
angles stall, you pivot the same product to skin/coat, then to longevity. You persist in the
product because the product was chosen to have somewhere to pivot **to**. If every buyer
problem has a huge TAM, making it work comes down to mechanism and delivery, not luck.

## Your action

1. List your product's core buyer problems.
2. Create one Manus project per buyer problem (start with your strongest one).
3. Name each project after the buyer problem, not the product.
